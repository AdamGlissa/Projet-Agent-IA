| 2 | Topic | **Literature review crew** |
| 3 | Target user | Master/PhD students, R&D engineers, and researchers starting a new research topic or writing a state-of-the-art document. |
| 4 | Problem and current pain | Searching arXiv, filtering relevant papers, reading a lot of abstracts and PDFs then synthesizing a structured and cited state of the art takes a lot of time (days of fastidious manual work). |
| 5 | What the agent does, in 3 sentences | Given a research question and constraints (keywords, date range), the system queries the arXiv API, retrieves and indexes relevant open-access papers, and extracts key information. A multi-agent workflow drafts a structured state-of-the-art review with inline citations and improves it through a reflection loop checking coverage and source accuracy. Before exporting the final report, the user reviews and approves the selected corpus and the final draft. |
| 6 | Success criterion (metric and target) | **Citation faithfulness & coverage** (We can imagine testing the agent on at least 10 research queries using RAGAS faithfulness and answer relevancy scores alongside a quick human check, while making sure no citations are made up). | |
| 7 | Architecture: orchestration and agentic patterns | **LangChain `deepagents` harness** (built on LangGraph `StateGraph`) with a main coordinator agent using **Planning (TODO list)**, **Filesystem working memory** (storing paper notes & drafts without context overflow), 3 specialized **Sub-agents** (**Researcher**, **Writer**, **Reviewer**), a **Reflection loop** (max 2 revisions), and **Human-in-the-Loop** approval before final export. |
| 8 | Tools: name, input, output, one line each | - `search_arxiv(query, max_results)` -> `list[dict]`: queries the arXiv API and returns basic metadata (title, authors, year, abstract, PDF link).<br>- `index_and_retrieve_papers(paper_ids, question)` -> `list[str]`: chunks abstracts/texts into ChromaDB and returns the top-k passages for the query.<br>- `export_review_markdown(filename, content)` -> `str`: saves the final review and BibTeX entries to a Markdown file after human approval (HITL).<br>- Built-in `deepagents` tools: `write_todos` (task list), `write_file` / `read_file` (notes and drafts), `task` (sub-agents). |
| 9 | Data sources: access, size, licence, personal data | • **arXiv API & Open-Access papers**: public REST API (`export.arxiv.org`), ~10–30 papers per query (JSON/XML + PDF text), arXiv / Creative Commons open-access licences, no personal/confidential data.<br>• **Evaluation dataset**: 10+ research topics with expected key papers and reference criteria. |
| 10 | Human approval point: which action, who approves | **Action**: Exporting the final state-of-the-art report (`export_review_markdown`, and corpus validation before drafting). **Who**: The user via DeepAgents `interrupt_on` + `Command(resume=...)`. |
| 11 | LLM and stack choices, with any change from the defaults | • **LLM**: `qwen2.5:7b` via Ollama (upgraded from `qwen2.5:3b` default for good tool calling, planning, and sub-agent delegation).<br>• **Embeddings & Vector Store**: `nomic-embed-text` + persistent `ChromaDB` (default TP2).<br>• **Orchestration & HITL**: `deepagents` (built on LangGraph `StateGraph` + `interrupt_on` / `Command(resume=...)`, extending TP4 with native planning, filesystem workspace, and sub-agents).<br>• **Evaluation & Observability**: `RAGAS` on 10+ test cases + `LangSmith` traces (non-confidential public arXiv data only).<br>• **Interface**: CLI / simple `Streamlit` UI (bonus). |
| 12 | Top 3 risks and fallback plan | **1. Made-up or wrong citations.** Fallback: every citation must match a paper returned by `search_arxiv` or a passage stored in ChromaDB; citations that don't match are removed or flagged, and the user checks them before export.<br>**2. The local 7B model is too weak for planning, tool calling or sub-agent delegation (wrong tool arguments, lost tasks, loops).** Fallback: short and strict prompts for each sub-agent, max 2 revisions, and if it still fails: a bigger model (`qwen2.5:14b`) or a simpler fixed flow (Researcher → Writer → Reviewer) in plain LangGraph.<br>**3. arXiv API is slow or blocks us (rate limit), PDFs can't be read, or runs are too slow on our laptops.** Fallback: local cache of search results, 3 s between calls, abstracts only when a PDF fails, max 30 papers per query and only top-k passages sent to the LLM; a ready corpus is saved for the demo topic. |
| 13 | Demo scenario for December 9, in 3 steps | **Step 1 – Ask and approve the corpus:** we type a question with constraints (e.g. "contrastive learning for image representation, 2020–2025"). The Researcher sub-agent searches arXiv and shows about 15 papers. The agent pauses (HITL): we remove one paper and approve.<br>**Step 2 – Plan, draft and reflect:** we show the coordinator's TODO list, the papers indexed in ChromaDB, the Writer's first draft, the Reviewer's comments and the improved draft (live in the LangSmith trace).<br>**Step 3 – Approve and export:** the agent pauses again before `export_review_markdown`; we approve, then show the Markdown file + BibTeX and the RAGAS scores on our test set (faithfulness, answer relevancy, no made-up citations).<br>**Backup:** a recorded run of the same demo, in case Ollama, the internet or the arXiv API fails. |
